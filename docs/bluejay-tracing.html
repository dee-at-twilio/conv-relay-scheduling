Trace your ConversationRelay agent with Bluejay

Bluejay's simulated customers take calls from your agent, and Bluejay scores each conversation. Send your app's OpenTelemetry trace, tool calls and a short call summary with every test call, and each score comes with a record of what your code did.

01

Why test with traces

Bluejay tests a voice agent with simulated customers, which it calls Digital Humans. A simulation runs a set of conversations between your agent and Digital Humans, and Bluejay's metrics score each one. In an outbound test, your agent calls the Digital Human, so the test runs through the same code that places your real outbound calls.

From the call itself, Bluejay knows what was said. It doesn't know what your app did: which tools ran, with what arguments, which ones failed, or how long each model request took. As Bluejay's metrics docs put it, "a transcript does not show tool calls." You fill that gap by attaching data to each test call's simulation result. This post sends three kinds:

DataWhat it isWhat Bluejay uses it for
trace_idsThe call's OpenTelemetry traceRequired by a Trace metric. Every metric also sees a summary of the linked trace.
tool_callsEach tool the agent called, with its arguments and resultRequired by a Tool Call metric
metadataJSON that describes the whole conversationEach key fills a dynamic variable in a metric prompt

Bluejay also accepts events, moments such as an escalation or a hold. They work the same way and are left out here to keep the code small.

A ConversationRelay app you wrote yourself doesn't record any spans until you ask it to. The changes are small: one file, bluejay.py, plus a few lines where your app starts, where it handles the WebSocket and where it runs tools. Your prompts and tools stay as they are.

The goal

Test the agent you ship, and let every test call carry a record of what your code did.

The examples come from a medical scheduling agent: a FastAPI app that serves ConversationRelay's TwiML at /incoming-call, handles the WebSocket at /ws, streams replies from OpenAI, and runs nine tools such as lookup_patient and schedule_appointment.

Before you start

A ConversationRelay app
An endpoint that returns <Connect><ConversationRelay> TwiML, and a WebSocket handler that receives ConversationRelay's messages. Your app places test calls with Twilio's REST API and points them at that same TwiML endpoint.
A Bluejay API key
Create one by following the "Get an API key" steps in Bluejay's API reference.
An Outbound Voice agent in Bluejay
Your app dials the Digital Human's phone number, so use the phone number connection described in Bluejay's outbound agents guide. You set its Outbound Trigger Webhook URL in section 07.
Digital Humans with phone numbers
Each Digital Human needs its own number, entered on its Connection tab. Your Twilio number must be able to call them.
A public HTTPS URL for your app
Bluejay POSTs to your app to start each test call, and Twilio fetches your TwiML from it. During development, a tunnel such as ngrok works.

03

Send traces to Bluejay

Bluejay receives spans over OTLP/HTTP at https://otlp.getbluejay.ai/v1/traces, with your API key in the X-API-KEY header. setup() installs a tracer provider that exports there, then turns on the OpenAI instrumentation:

src/bluejay.py · setup
BLUEJAY_TRACES_URL = "https://otlp.getbluejay.ai/v1/traces"


def setup() -> None:
    """Send OpenTelemetry traces to Bluejay. Does nothing unless BLUEJAY_API_KEY is set."""
    api_key = config.bluejay_api_key
    if not api_key:
        return
    provider = TracerProvider(resource=Resource.create({SERVICE_NAME: "conv-relay-scheduling"}))
    # Batches on a background thread, so calls never block on Bluejay.
    provider.add_span_processor(
        BatchSpanProcessor(
            OTLPSpanExporter(endpoint=BLUEJAY_TRACES_URL, headers={"X-API-KEY": api_key})
        )
    )
    trace.set_tracer_provider(provider)
    OpenAIInstrumentor().instrument(tracer_provider=provider)
    logger.info("Bluejay tracing enabled")
  • BatchSpanProcessor instead of Bluejay's SimpleSpanProcessor. A simple processor exports each span as soon as it ends, on the thread that ended it, which here is the event loop serving your calls. The batch processor exports in the background. Before a call is linked, bluejay.py calls force_flush(), as Bluejay's guide requires (section 06).
  • OpenAI requests are traced with no code from you. OpenAIInstrumentor wraps the OpenAI SDK, so every chat.completions.create call becomes an openai.chat span carrying the model, messages, tool calls and token counts. For a streamed reply, the span ends when the stream has been read to the end.
Read the key from your settings, not os.environ

pydantic-settings loads .env into your settings object but doesn't copy it into os.environ. A setup() that reads os.environ["BLUEJAY_API_KEY"] finds nothing and silently does nothing. Read config.bluejay_api_key instead, and log a line when tracing turns on so you can see it did.

Checkpoint

Restart the app. The startup log should show Bluejay tracing enabled.

04

Give each call one trace

With only setup() in place, every OpenAI request has no parent span, so OpenTelemetry starts a new trace for each one. Bluejay would see a dozen one-span traces per call, with nothing to say they belong together, and no single trace ID to attach to the result.

The fix is one span that covers the whole call. Open it around the loop that serves the ConversationRelay WebSocket, and make it current:

src/twilio/websocket_receiver.py
from opentelemetry import trace

from src import bluejay
...
tracer = trace.get_tracer(__name__)


async def handle_relay_websocket(ws: WebSocket) -> None:
    ...
    if params.get("session_id") and params.get("role"):
        await _run_bridge_loop(ws, sender, setup)
    else:
        with tracer.start_as_current_span("call", attributes={"call.sid": setup.callSid}) as call_span:
            await _run_agent_loop(ws, sender, setup)
        await bluejay.link_simulation(call_span, setup.callSid)
  • The span starts when ConversationRelay's setup message arrives and ends when the WebSocket closes, after a hangup or a handoff.
  • Every span created during the call lands under it. The handler starts each caller turn with asyncio.create_task(process_turn(...)), and a task copies the current context when it's created. So the OpenAI spans inside each turn find call as their parent, even with several calls in progress at once. You don't pass a trace ID around.
  • Opening the span at the call site keeps _run_agent_loop as it was, with no reindenting.
  • The last line links the call to its result once the span has ended (section 06).

Add spans for the rest of your app

The trace above doesn't show the tools themselves, or which requests belong to which caller turn. Add a span to any step you want to see, such as a tool, a database lookup or a guardrail check, with the plain OpenTelemetry API. Anything you open while a call is in progress nests under call:

your agent code
from opentelemetry import trace

tracer = trace.get_tracer(__name__)

with tracer.start_as_current_span("tool.schedule_appointment") as span:
    result = await tool_registry.run(tc.name, tc.arguments, state)
    span.set_attribute("tool.success", result.success)

To add something to the span that's already open, without starting a new one, use trace.get_current_span().set_attribute(...) or .add_event(...).

Pick span names you can match on. A Trace metric checks for span names only (section 07), so use a fixed name like tool.schedule_appointment, and put changing values such as IDs in attributes.

05

Trigger the test call

In an outbound test, the Digital Humans wait on their lines until your agent reaches them or the run times out. Bluejay can't make your agent dial, so it asks your app to: it POSTs once per conversation to the agent's Outbound Trigger Webhook URL. Bluejay rejects the run if the URL is empty.

The trigger also matters for tracing. It's the only place Bluejay tells your app which simulation result a call belongs to. An app that receives the trigger and places the call can link its trace to that result exactly.

What Bluejay sends

PartValue
phone_numberThe Digital Human's number, in E.164
sim_conversation_idThe ID of this conversation in the simulation
X-Bluejay-Idempotency-KeyThe conversation ID. Bluejay's docs say to use it to ignore a repeated request.
X-Bluejay-SignatureAn HMAC-SHA256 of the raw body, signed with the agent's Webhook Signing Key. This route doesn't check it (see below).

Your app must return a 2xx within 15 seconds. After 3 failed tries, Bluejay ends the conversation with OUTBOUND_TRIGGER_FAILED. The body above is the default. If you set a custom body template on the agent, the route has to read your fields instead.

The trigger route

The route dials the Digital Human's phone number with Twilio's REST API. The call's url is the app's existing /incoming-call endpoint, so the test call gets the same ConversationRelay TwiML, and runs through the same WebSocket handler, as any other call:

src/bluejay.py · /bluejay/trigger-call
router = APIRouter()

# Test calls this app placed: idempotency key -> call SID, and call SID -> (result ID, idempotency key).
_triggers: dict[str, str] = {}
_simulations: dict[str, tuple[str, str]] = {}


@router.post("/bluejay/trigger-call")
async def trigger_call(request: Request) -> dict:
    """Bluejay's outbound trigger: call the Digital Human and remember which result the call belongs to."""

    data = await request.json()
    phone_number = data.get("phone_number")
    result_id = str(data.get("sim_conversation_id") or "")

    if not phone_number or not result_id:
        raise HTTPException(status_code=400, detail="phone_number and sim_conversation_id are required")
    trigger_key = request.headers.get("X-Bluejay-Idempotency-Key") or result_id

    if trigger_key in _triggers:
        return {"status": "ok", "call_sid": _triggers[trigger_key]}

    client = Client(config.twilio_account_sid, config.twilio_auth_token)

    call = await asyncio.to_thread(
        client.calls.create, to=phone_number, from_=config.twilio_phone_number, url=config.http_url + "/incoming-call"
    )
    _triggers[trigger_key] = call.sid
    _simulations[call.sid] = (result_id, trigger_key)
    logger.info("Bluejay test call placed to=%s callSid=%s result_id=%s", phone_number, call.sid, result_id)
    return {"status": "ok", "call_sid": call.sid}

The route does three things, in order:

  • It places the call once. Bluejay retries a trigger that doesn't get a 2xx. A retry carries the same idempotency key, so the route returns the call it already placed.
  • It answers quickly. The Twilio client blocks, so calls.create runs in a thread with asyncio.to_thread, and the event loop keeps serving calls in progress. The route returns as soon as Twilio accepts the call, well inside Bluejay's 15 seconds.
  • It remembers which result the call belongs to. Your app places the call, so it has the Call SID before the call connects. The route stores the result ID under that Call SID. When ConversationRelay connects the call, its setup message carries the same Call SID, and link_simulation looks the result ID up by it (section 06).
This route doesn't check the signature

To keep the code small, the route skips X-Bluejay-Signature. Anyone who finds the URL can make your app place calls from your Twilio number. That's acceptable for a test behind a tunnel. Before you leave it running anywhere else, verify the signature as Bluejay's webhook docs describe: an HMAC-SHA256 of the raw request bytes, read with await request.body() before parsing, compared with hmac.compare_digest.

Not in Bluejay's guides: is sim_conversation_id the simulation result ID?

Bluejay's Traces guide says to read the result ID from an X-Simulation-Result-Id header that comes with a SIP call. A call your app places never receives that header. The trigger docs send sim_conversation_id, but don't say it's the same ID. Bluejay's API spec treats them as the same: one field description says to read the result ID "from the X-Simulation-Result-Id SIP header … or the sim_conversation_id dynamic variable". This post relies on that, and linking with it worked in testing. If linking returns 404, check this first.

06

Attach the call to its result

Bluejay's docs describe the same flow for every agent:

  1. While the call runs, record its tool calls (and any events and metadata).
  2. After the call ends, call force_flush() on the tracer provider. Otherwise, the docs warn, "the trace can be missing."
  3. Send everything to POST https://api.getbluejay.ai/v1/update-simulation-result, with your API key in the X-API-Key header.

Record tool calls and metadata

bluejay.py keeps what each call records in memory, keyed by Call SID, until the call is linked. Both functions do nothing unless BLUEJAY_API_KEY is set:

src/bluejay.py · record_tool and set_metadata
# Tool calls and metadata recorded during each call, keyed by call SID; sent when the call is linked.
_recorded: dict[str, dict] = {}


def _record(call_sid: str) -> dict:
    return _recorded.setdefault(call_sid, {"tool_calls": [], "metadata": {}})


def record_tool(call_sid: str, name: str, parameters: dict, output: Any) -> None:
    """Record a tool call for Bluejay's Tool Call metric."""
    if config.bluejay_api_key:
        _record(call_sid)["tool_calls"].append(
            {"name": name, "parameters": parameters, "output": output, "time_ns": time.time_ns()}
        )


def set_metadata(call_sid: str, metadata: dict) -> None:
    """Set call-level values; each key fills a {{variable}} in Bluejay metric prompts."""
    if config.bluejay_api_key:
        _record(call_sid)["metadata"].update(metadata)

Tool calls. Every tool the scheduling agent has runs through one line, tool_registry.run, so one call to record_tool right after it covers all nine. It records the tool's name, the arguments the model passed, and the result, or the error if the tool failed:

src/orchestration/conversation_graph.py · process_turn
for tc in tool_calls:
    logger.info("executing tool=%s callSid=%s", tc.name, state.call_sid)
    result = await tool_registry.run(tc.name, tc.arguments, state)
    bluejay.record_tool(
        state.call_sid, tc.name, tc.arguments, result.data if result.success else {"error": result.error}
    )

Metadata. When the WebSocket loop ends, the handler sums up the call from the session state it already keeps. Each key becomes a variable you can use in a metric prompt. Patient names and phone numbers are left out, because they're personal data:

src/twilio/websocket_receiver.py · _run_agent_loop
    finally:
        bluejay.set_metadata(call_sid, _call_metadata(state))
        session_manager.end_session(call_sid)
        event_bus.publish(SessionEvent(call_sid=call_sid, event="ended"))


_OUTCOMES = {"schedule_appointment": "booked", "reschedule_appointment": "rescheduled", "cancel_appointment": "cancelled"}


def _call_metadata(state: SessionState) -> dict:
    """Summarize the call for Bluejay metric prompts. Leaves out names and phone numbers (PII)."""
    results = [json.loads(m.content) for m in state.messages if m.role == "tool"]
    succeeded = {r["tool_name"] for r in results if r["success"]}
    return {
        "outcome": ", ".join(o for tool, o in _OUTCOMES.items() if tool in succeeded) or "no_action",
        "patient_identified": state.patient_id is not None,
        "final_language": state.language,
        "turns": sum(m.role == "user" for m in state.messages),
        "tool_failures": sum(not r["success"] for r in results),
    }

The fields come from Bluejay's API reference:

Tool call fieldRequiredSet by bluejay.py
nameYesThe tool's name. A Tool Call metric matches on it.
start_offset_msYesWhen the tool ran, in milliseconds from the start of the call span
parametersNoThe arguments the model passed
outputNoWhat the tool returned, or {"error": ...}
Where offsets start

Bluejay counts offsets "from the start of the call". bluejay.py counts them from when the call span starts, which is when ConversationRelay connects the call to your app. Bluejay's docs don't say exactly when its clock starts, so the two may differ by the time it takes the call to connect.

Send it when the call ends

link_simulation runs once per call, after the call span ends. It builds one request from the trace ID, the result ID the trigger route stored, and whatever was recorded:

src/bluejay.py · link_simulation
BLUEJAY_LINK_URL = "https://api.getbluejay.ai/v1/update-simulation-result"


async def link_simulation(call_span, call_sid: str) -> None:
    """Send a finished call's trace, tool calls and metadata to its Bluejay simulation result."""
    if not config.bluejay_api_key:
        return
    recorded = _recorded.pop(call_sid, {"tool_calls": [], "metadata": {}})
    simulation = _simulations.pop(call_sid, None)
    body: dict[str, Any] = {"trace_ids": [format(call_span.get_span_context().trace_id, "032x")]}
    if simulation is not None:  # placed by trigger_call, so the result ID is known
        result_id, trigger_key = simulation
        _triggers.pop(trigger_key, None)
        body["simulation_result_id"] = result_id
    else:  # let Bluejay match the call by time
        start, end = call_span.start_time / 1e9, call_span.end_time / 1e9  # SDK spans record ns
        body["start_time"] = datetime.fromtimestamp(start, timezone.utc).isoformat()
        body["end_time"] = datetime.fromtimestamp(end, timezone.utc).isoformat()
        body["duration"] = end - start
    if recorded["tool_calls"]:
        body["tool_calls"] = [
            {
                "name": tc["name"],
                "parameters": tc["parameters"],
                "output": tc["output"],
                "start_offset_ms": max(0, (tc["time_ns"] - call_span.start_time) // 1_000_000),
            }
            for tc in recorded["tool_calls"]
        ]
    if recorded["metadata"]:
        body["metadata"] = recorded["metadata"]

    # Spans are batched; push them out before Bluejay looks the trace up.
    await asyncio.to_thread(trace.get_tracer_provider().force_flush)
    try:
        async with httpx.AsyncClient(timeout=10) as client:
            resp = await client.post(
                BLUEJAY_LINK_URL,
                content=json.dumps(body, default=str),  # tool outputs may not be plain JSON
                headers={"X-API-Key": config.bluejay_api_key, "Content-Type": "application/json"},
            )
    except httpx.HTTPError:
        logger.exception("Bluejay link request failed")
        return
    if resp.is_error:
        logger.warning("Bluejay link failed status=%s body=%s", resp.status_code, resp.text)
    else:
        logger.info(
            "Bluejay trace linked trace_id=%s result_id=%s tool_calls=%d",
            body["trace_ids"][0],
            body.get("simulation_result_id", "matched by time"),
            len(body.get("tool_calls", [])),
        )
  • One request per call. The trace, every tool call and the metadata go together. The spans themselves were already sent in batches while the call ran.
  • The trace ID goes in hex. OpenTelemetry stores it as an integer. Bluejay expects the usual 32-character hex form.
  • The flush runs off the event loop. force_flush() blocks until the batch is exported, so it runs in a thread.
  • Calls the trigger didn't place still get linked. Without a result ID, the request sends start_time, end_time and duration, and Bluejay matches the call by time. That match is looser: Bluejay returns 409 and writes nothing when several calls fit.
  • Failures are logged, not retried. Bluejay returns 404 when no result matches, 409 when the match is ambiguous, and 422 for an invalid body. None of them affects the call, which has already ended.
07

Write metrics and run a test

Three kinds of metric read the data from section 06. In the scheduling agent they check different things:

MetricHow it passesScheduling example
Tool CallThe agent called every listed tool, matched by the name you sent in tool_callsList schedule_appointment: the agent actually booked when asked to
TraceThe linked trace contains (or doesn't contain) every listed span nameContains openai.chat today. With tool spans from section 04, contains tool.lookup_patient.
LLM as a JudgeA model grades the conversation against your prompt, which can use metadata keys"The app reports outcome {{outcome}}. Does the transcript agree?"
  • A Trace metric matches span names only. Its type is trace_span. You set span_names and a condition of contains or does_not_contain. Names are matched without regard to case, and Bluejay suggests names it has seen in your recent traces. A conversation with no linked trace fails unless Allow Not Applicable is on.
  • Every metric sees a summary of the linked trace, so even a judge metric that never mentions it can use what the trace shows.

What you seeWhat it means

Things to know

  • Run a single instance. The trigger route and the recordings are held in the app's memory, so the instance that gets the trigger must also handle the call.
  • Don't share a Digital Human's number between simulations that run at the same time. If a newer simulation takes the number mid-test, Bluejay stops the earlier test with SIP_TRUNK_RECYCLED.
  • Model requests carry the conversation. The OpenAI instrumentation records the messages in each request and the reply, so what the caller says goes to Bluejay in the trace. Check the instrumentation's docs for how to turn off content capture if that doesn't fit your data policy.
  • Use trace_ids, not trace_id. Bluejay's Monitor Traces page mentions trace_id, but the API reference marks it as deprecated in favor of trace_ids.
08

The same code in production

Nothing in bluejay.py is test-only except the trigger route. With the key set, the exporter sends every call's spans, real callers included, to the same endpoint. The recordings for a call that no trigger placed are sent with a time-window match, which finds no simulation result for a real caller and is logged as a failure.

To score a real call and show its trace beside it, send the conversation to POST /v1/evaluate. According to Bluejay's API reference, it requires:

  • agent_id or external_agent_id.
  • start_time_utc. Transcript, tool-call and event offsets count from this moment.
  • participants: one AGENT and one USER.
  • The conversation itself: a transcript, a transcript_url or a recording_url.

It also takes the same trace_ids, tool_calls and metadata as a test call. bluejay.py doesn't send production calls yet. The app would need to build the transcript, which it already sees turn by turn on the WebSocket, and call /v1/evaluate instead of update-simulation-result for calls the trigger didn't place.
